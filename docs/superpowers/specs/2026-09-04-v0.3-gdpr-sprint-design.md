# v0.3: metadata-only capture, subject transparency, per-record erasure

Design spec, 2026-09-04. Implements the three GDPR items from `ROADMAP.md`
v0.3: `capture.bodies: false`, the subject-transparency view for Article 15
access requests, and a chain-preserving per-record erasure path for Article 17.

## Goals

- Let a deployer run upbox without storing prompt bodies or headers at all,
  persistently and visibly, with the setting disclosed in every export.
- Answer "what does upbox hold about me" with one artefact a person can be
  handed, generated by one command and mirrored by one dashboard page.
- Erase individual records on request without the audit log reading as
  tampered with, and without hiding that an erasure happened.
- Keep every existing hash valid. `CHAINED_FIELDS` does not change. A v0.2
  database migrates in place with three nullable columns.

## Non-goals

- Team mode, the workplace deployment pack, native binaries (still v0.3+
  roadmap, separate work).
- Erasure from the dashboard. The dashboard stays read-only; erasure is a CLI
  write like `prune` and `hold`.
- Per-tool or per-host capture policies. One global policy.
- Response bodies. upbox has never stored them and still does not.
- Separating third-party personal data inside a captured prompt from the
  user's own. The report states this limitation instead.

## Background: the states a row can already be in

`requests` rows carry `body_excerpt` and `headers_json` as the two content
columns. Retention clears them and records `pruned_at` plus `pruned_fields`.
The hash chain commits to `body_excerpt_sha256` and `headers_sha256` rather
than the text, so clearing the text keeps `upbox verify` passing while the
count of cleared rows is disclosed as `content_unavailable`. Whole-row
deletion is only possible as a contiguous run from the oldest entry and is
recorded in `chain_gaps`. Rows written before v0.2 have `seq IS NULL` and sit
outside the chain.

v0.3 adds two more states, each explicit in the row: content **never stored**
by capture policy, and a row **erased on request**.

## 1. Capture policy: `capture.yaml`

### File

Bundled at `upbox/rules/capture.yaml`, user override at
`~/.upbox/rules/capture.yaml`, same precedence as the other rule files.

```yaml
# What upbox stores per request beyond metadata. Metadata (timestamp, tool,
# host, path with credentials removed, sizes, status, body SHA-256, redaction
# and enforcement outcomes) is always kept.
#
# bodies:  store the request body excerpt (up to 100 KB, after redaction).
#          body_hash and req_bytes are recorded either way.
# headers: store request headers. Credential values are always replaced with
#          [REDACTED:header] before storage, whatever this says.
#
# Both false is metadata-only mode: the recommended configuration on machines
# you do not own. Copy this file to ~/.upbox/rules/capture.yaml to change it.
bodies: true
headers: true
```

### Loading

`upbox/addons/capture.py` gains:

- `DEFAULT_RULES_RESOURCE = "capture.yaml"`, `USER_RULES_PATH`, following the
  other addon modules so `watch.build_rule_watch_targets` and
  `audit_export.ruleset_digests` can point at them.
- `@dataclass(frozen=True) class CapturePolicy: bodies: bool = True;
  headers: bool = True`, with `omitted_columns() -> tuple[str, ...]`
  returning the subset of `("body_excerpt", "headers_json")` it withholds and
  `is_metadata_only` as a property.
- `load_policy() -> CapturePolicy`. Bundled file when no user file exists.
  A user file that is unreadable, not a mapping, or has a non-boolean value
  for `bodies` or `headers` yields **metadata-only** and logs an error. The
  file's existence signals intent to restrict; over-collecting is the
  irreversible direction, so the fallback is the restrictive one. Unknown
  keys are ignored with a warning. Missing keys take the bundled default.
- `CaptureAddon.__init__(self, store, policy: CapturePolicy | None = None)`.
  `None` calls `load_policy()`. `CaptureAddon.reload()` re-reads the file
  and swaps the policy; on failure it keeps the previous policy and logs,
  matching `EnforceAddon.reload`.

`settings.SCHEMAS` gains `"capture": dict`, and `_structurally_valid` checks
that keys are a subset of `{"bodies", "headers"}` and values are booleans,
so the dashboard settings page gets a fourth editor. The settings page
footer text changes from "Restart `upbox start` to apply" to the live-reload
wording already used in the save message.

`watch.build_rule_watch_targets(fingerprint, redact, enforce, capture)`
adds `(capture.USER_RULES_PATH, capture.reload)`. `proxy._run` passes the
capture addon it already constructs.

### What a row looks like

`_record_from_flow` becomes an instance method reading `self._policy`:

- `bodies: false`: `body_excerpt = None`. `body_hash` and `req_bytes` are
  still computed from the real body.
- `headers: false`: `headers_json = None`.
- New column `omitted_fields`: JSON list of the withheld column names, or
  `NULL` when nothing was withheld. Mirrors `pruned_fields`.

`RequestRecord` gains `omitted_fields: str | None = None` as its last
field, so `jsonl` and `csv` exports pick it up through `_csv_fieldnames`.
`_INSERT_COLUMNS` and the placeholder count grow by one.

The chain sees `body_excerpt_sha256 = None` and `headers_sha256 = None`,
exactly as it does for a pruned row. `CHAINED_FIELDS` is unchanged.
Redaction still runs before forwarding and `redactions_applied_json` is
still recorded: the policy changes what is stored, not what is sent.

### Retention interaction

`Store.prune` and `Store.preview_prune` add
`AND (body_excerpt IS NOT NULL OR headers_json IS NOT NULL)` to the body
tier, so rows with nothing left to clear are neither counted nor stamped
with `pruned_at`. Existing behaviour for rows that have content is unchanged
(an empty-string body still counts as content, as today).

### Disclosure

- **Dashboard.** Body tab renders one of: the excerpt; "Not stored:
  capture.yaml has bodies: false. Size and SHA-256 were recorded." when
  `omitted_fields` names `body_excerpt`; "Cleared by retention on
  {pruned_at}. Digest recorded." when `pruned_fields` names it; "(empty)"
  otherwise. Headers tab does the same with `headers_json`. The stats bar
  shows a `capture: metadata-only` badge when both are off, reading the
  policy through `load_policy()` at render time.
- **Audit export.** `ruleset_digests()` gains `capture_sha256`. The header
  `chain` block gains `content_omitted_by_capture_policy` (count of rows
  with `omitted_fields IS NOT NULL`, from a store query). Each record gains
  `"capture": {"omitted_fields": [...] | null}`; `body_truncated` is `null`
  when the body was omitted, matching the pruned case, because truncation
  of a body that was never stored is not a checkable claim.
- **CLI.** `upbox doctor` prints `Capture policy: bodies=…, headers=…`.

## 2. Erasure: `upbox erase`

### Command

```
upbox erase --reason TEXT [--id N ...] [--host HOST] [--tool TOOL]
            [--since TS] [--until TS] [--dry-run]
```

- `--reason` is required and non-empty; it is stored on every tombstone.
- At least one selector is required. Selectors AND-combine: `id IN (...)`,
  `host = ?` (exact), `tool = ?` (exact), `ts >= ?`, `ts <= ?`. Time bounds
  are normalised with the existing `_normalise_bound`, so a bare date covers
  the whole day.
- Already-erased rows never match.
- **Legal hold refuses the whole operation.** If any matching row has
  `legal_hold = 1`, nothing changes, the held ids are listed, exit code 1,
  with the instruction to `upbox hold --release` first. A hold means stop,
  not work around.
- `--dry-run` prints the match count, the first 20 ids, and the oldest and
  newest timestamps, and changes nothing.
- On success: `erased N row(s) (ids …). Tombstones keep seq, hashes and
  timestamp; content is gone. upbox verify reports them as erased on
  request.` Unchained rows (pre-v0.2) are deleted outright and reported
  separately: they have no chain position to preserve.

### Store API

```python
@dataclass(frozen=True)
class EraseSelection:
    ids: tuple[int, ...] = ()
    host: str | None = None
    tool: str | None = None
    since: str | None = None
    until: str | None = None
    def is_empty(self) -> bool: ...

@dataclass(frozen=True)
class EraseResult:
    erased: int            # chained rows turned into tombstones
    deleted_unchained: int # pre-v0.2 rows removed outright
    ids: tuple[int, ...]

class LegalHoldError(RuntimeError):
    held_ids: tuple[int, ...]

Store.preview_erase(selection) -> list[sqlite3.Row]   # matching, not yet erased, holds included
Store.erase(selection, reason, now=None) -> EraseResult  # raises LegalHoldError before writing
```

The tombstone update, one `BEGIN IMMEDIATE` transaction:

```sql
UPDATE requests SET
  tool = NULL, method = NULL, scheme = NULL, host = NULL, path = NULL,
  req_bytes = NULL, resp_bytes = NULL, status = NULL,
  headers_json = NULL, body_excerpt = NULL, body_hash = NULL,
  redactions_applied_json = NULL, enforcement = NULL,
  headers_sha256 = NULL, body_excerpt_sha256 = NULL,
  pruned_at = NULL, pruned_fields = NULL, omitted_fields = NULL,
  erased_at = ?, erased_reason = ?
WHERE id IN (...) AND seq IS NOT NULL AND legal_hold = 0 AND erased_at IS NULL
```

What survives: `id`, `ts`, `seq`, `prev_hash`, `entry_hash`, `legal_hold`
(always 0 here), `erased_at`, `erased_reason`. `ts` stays because
verification order and `record_days` retention still need it; a timestamp
with nothing attached is the minimum that keeps the log coherent.

### Verification

`verify_chain` handles a row with `erased_at IS NOT NULL` as a tombstone:

- Sequence continuity and `prev_hash == expected_prev` are checked as for
  any row.
- `entry_hash` is **not** recomputed (the inputs are gone). It becomes
  `expected_prev` for the next row.
- A tombstone in which any of the fifteen columns the tombstone UPDATE
  nulls (`tool` through `body_excerpt_sha256` in the statement above) is
  still non-null is reported as **broken** (`seq N is marked erased but
  still carries content`). Without this, marking a row erased would be a
  way to skip recomputation while leaving altered content in view.
- `ChainVerification.entries_erased` counts them. `checked` continues to
  count recomputed entries only.

`upbox verify` prints: `N entry/entries were erased at the data subject's
request. Their hashes still link; their content cannot be re-checked.` The
README's tamper-evidence section states the trust model plainly: an erasure
is disclosed, not hidden, and a tampered row that has been tombstoned is
indistinguishable from a legitimate erasure except by that disclosure, which
is the same position retention gaps are already in.

### Retention interaction

Tombstones keep `ts`, so `record_days` deletes them in the normal contiguous
run and they are counted in `chain_gaps` like any row. The body tier skips
them (nothing left to clear). `upbox hold` may be applied to a tombstone;
it protects only the tombstone itself.

### Export

Tombstoned records are emitted (an audit file that silently dropped them
would understate the log). Content fields are `null`; the record gains
`"erased": {"at": ..., "reason": ...}` (or `"erased": null` for live rows);
`body_truncated` and `enforcement_meaning` are `null`; the `chain` block is
present as usual. The header `chain` block gains
`entries_erased_on_request`.

`Store.query_filtered` gains `include_erased: bool = False`. The audit export
passes `True`; the dashboard, `jsonl`, and `csv` paths keep the default and
never see tombstones. `query_recent`, `dashboard_stats`, and
`per_tool_summary` add `WHERE erased_at IS NULL`.

### Dashboard

The feed, tiles, and stats exclude tombstones. Opening `/requests/{id}` for
an erased row renders a tombstone panel instead of the tabs: id, `ts`,
`erased_at`, reason, and one line saying the chain still links through it.
The transparency page lists erasures (see section 3).

## 3. Transparency report: `upbox report` and `/transparency`

### Data model, `upbox/report.py`

```python
@dataclass(frozen=True)
class Recipient:
    tool: str; host: str; requests: int; req_bytes: int; first_seen: str; last_seen: str

@dataclass(frozen=True)
class Erasure:
    request_ts: str; erased_at: str; reason: str

@dataclass(frozen=True)
class Checkpoint:
    ts: str; seq_end: int; head_hash: str

@dataclass(frozen=True)
class TransparencyReport:
    generated_at: str
    upbox_version: str
    hostname: str            # platform.node()
    os_user: str             # getpass.getuser(), "unknown" on failure
    database_path: str
    capture_bodies: bool
    capture_headers: bool
    rows_with_omitted_content: int
    body_days: int | None
    record_days: int | None
    rows_with_pruned_content: int
    entries_deleted_by_retention: int   # sum over chain_gaps of (seq_end - seq_start + 1)
    rows_under_legal_hold: int
    total_rows: int          # live rows, tombstones excluded
    first_ts: str | None
    last_ts: str | None
    total_req_bytes: int
    body_excerpt_max: int
    recipients: tuple[Recipient, ...]
    erasures: tuple[Erasure, ...]
    chain_status: str
    chain_checked: int
    chain_entries_erased: int
    chain_head_hash: str
    last_checkpoint: Checkpoint | None

def build_report(store, *, capture_policy=None, retention_policy=None) -> TransparencyReport
def render_markdown(report) -> str
def render_json(report) -> str      # dataclasses.asdict + json.dumps, indent 2
```

`build_report` loads the two policies from their files when not injected
(tests inject). It only reads; it works on a read-only store, which is what
the dashboard has. New store queries: `recipients()` (group by tool, host
over live rows), `erasures()`, `report_counts()` (omitted, pruned, held,
erased), `deleted_entry_count()`, `latest_checkpoint()`.

### Markdown layout

1. **Title and scope.** "What upbox holds about this machine's user."
   Generated at, upbox version, hostname, OS user, database path. One line:
   "Controller and contact: to be completed by the deployer." upbox cannot
   know who the controller is; the line makes the gap explicit rather than
   omitting it.
2. **Purpose.** Static: deployer-side observation of AI-tool network
   traffic, to see, redact, and control what leaves the machine. Not legal
   advice.
3. **Categories of data and whether they are stored.** A table over:
   timestamp; tool; destination host; path (credential values removed);
   request and response sizes; HTTP status; request headers (credential
   values replaced); request body excerpt up to `body_excerpt_max` after
   redaction; SHA-256 of the full redacted body; redaction and enforcement
   outcomes. The two content rows show "stored" or "not stored (capture
   policy)" from the live policy, plus the pruned-row count.
4. **Recipients.** Per tool and host: request count, bytes, first and last
   seen. These are the organisations that received the data.
5. **Retention.** `body_days`, `record_days`, rows with cleared content,
   entries deleted by retention, rows under legal hold.
6. **Erasures.** Count, then one line each: request timestamp, erased at,
   reason. "None" when empty.
7. **Integrity.** Chain status, entries checked, entries erased, head hash,
   last checkpoint.
8. **Your rights and how to exercise them.** Copy of the records:
   `upbox export --format audit -o records.ndjson` (or `upbox report
   --records`). Erasure: `upbox erase --id N --reason "..."`. Retention
   changes: `~/.upbox/rules/retention.yaml`. Storing less:
   `~/.upbox/rules/capture.yaml`.
9. **Limitations.** The existing coverage note; bodies may contain personal
   data of third parties that upbox cannot separate from the user's own;
   timestamps are host wall clock; erasures are disclosed, not hidden.

No em-dashes anywhere in the rendered text.

### CLI

```
upbox report [-o FILE] [--format md|json] [--records FILE]
```

Default `md` to stdout. `--records FILE` additionally writes an
`upbox.audit.v1` export of every row, tombstones included, so one command
produces both the readable report and the machine-readable copy. Opens the
store as a writer like the other commands, so it also migrates.

### Dashboard

`GET /transparency` renders `templates/transparency.html` (extends
`base.html`) from `build_report(store)` on the read-only store. The sidebar's
placeholder "Audit" link becomes "Transparency" pointing here, on both the
index and settings sidebars. Same sections as the Markdown, same order.

## 4. Schema: migration v4 and the read-only guard

- `SCHEMA_VERSION = 4`. `_migrate_v4_subject_rights` adds, when absent:
  `omitted_fields TEXT`, `erased_at TEXT`, `erased_reason TEXT`. All
  nullable, no rewrite, no index.
- `schema.sql` adds the same three columns with comments explaining the two
  new states. `test_fresh_and_migrated_schemas_match` keeps both paths
  honest.
- `Store.schema_version` becomes a public read-only property.
- **Read-only guard.** `create_app` records
  `app.state.schema_behind = store.schema_version < SCHEMA_VERSION` in the
  lifespan. An HTTP middleware returns a 503 HTML page for every path except
  `/static/*` while that is true: "This database is at schema version N;
  this upbox needs M. Run `upbox start` or `upbox verify` once to migrate.
  The dashboard never modifies your data." Without this, a user who upgrades
  and runs only `upbox dashboard` would hit template errors on the new
  columns.
- Upgrading needs no user action: the first writer (`upbox start`, `proxy`,
  `verify`, `prune`, `hold`, `checkpoint`, `export`, `erase`, `report`)
  migrates. Existing hashes are untouched; `upbox verify` passes before and
  after.

## 5. Error handling

- Capture policy: malformed user file at boot yields metadata-only plus an
  error log; a failed reload keeps the previous policy. Never raises into
  mitmproxy.
- Erase: `LegalHoldError` is raised before any write; the CLI prints the
  held ids and exits 1. An empty selection exits 2 with usage text. A
  selection matching nothing prints `nothing to erase` and exits 0.
- Report: `getpass.getuser()` failures yield `"unknown"`. A broken chain is
  reported, not raised. Missing policy files yield defaults, as today.
- Dashboard: an erased row's detail renders the tombstone panel; unknown id
  stays 404.

## 8. Decisions taken

- Rules file rather than a CLI flag for capture policy: it must survive
  restarts, be editable where the other rules are, and be digested into the
  export.
- Malformed capture file fails to metadata-only, not to full capture.
- Tombstones wipe everything except `ts` and the chain skeleton.
- Dashboard stays read-only; erasure is CLI only.
- One report generator, two renderers.
- Tombstones appear in the audit export and never in the dashboard feed.
